# OpenJarvis — Master Build Handoff Prompt

Build a production-quality Android assistant named **OpenJarvis** using this project as the product specification and UI/backend reference. Product principle: **Simple Outside. Powerful Inside.**

## Non-negotiable UX
- The first screen is a clean ChatGPT-like chat, not a dashboard or grid of feature cards.
- Keep the existing OpenJarvis logo style and premium dark navy / electric blue / subtle violet identity.
- Profile display name is exactly **Ravi**. In chat, the user's avatar/label is **U**, not Ravi.
- Two selectable personas only: **Adam (Male)** and **Kajal (Female)**. The user selects one in Settings. Only the selected persona speaks in that conversation; never show both responding to one message.
- Do not show human faces for the AI personas. Use distinctive abstract/silhouette avatar illustrations, Adam blue and Kajal violet/pink, consistent across header and message bubbles.
- Chat composer supports text, image, file/document and voice input. Keep controls compact.
- Sidebar: New Chat, History, Clear Chat, Settings, About. Creator credit links to CRAFTER RAVI YouTube.
- No fake premium subscription labels. Do not invent a Premium User badge.
- Responsive mobile-first design, accessible contrast, keyboard support, loading, empty, error, offline and permission states.

## Core app modules (progressively revealed, not crowded on home)
1. AI chat and persona selection.
2. Provider settings: one configured provider is sufficient; support Gemini, OpenAI, Anthropic and DeepSeek adapters. Store keys server-side or in Android Keystore; never expose them in frontend source or logs.
3. Voice mode: Hindi and English, selectable voice, interrupt/stop, explicit mic state. Use only currently supported provider models and verify availability at implementation time.
4. Device automation: AccessibilityService, MediaProjection for screen capture, notifications access and runtime permissions as separately consented features. Add a visible automation indicator, action log, global Stop, per-task confirmation and safe recovery.
5. File/image input with size limits and clear processing status.
6. Local chat history and optional encrypted local notes. Offer export/delete controls.
7. Offline mode: optional small quantized on-device model and local knowledge retrieval; explain model download size, RAM and storage requirements. Do not claim that a tiny database equals billions of facts.
8. Lite / Cloud / Remote PC modes: local lightweight tasks on phone; heavy builds, GPU workloads and large media processing on cloud/remote workstation. Clearly disclose network, API, billing and account requirements.
9. Future tools: code workspace, web/app builder, terminal, Git, database tools, media workflows, research/browser and Free Fire Craftland helper. Keep these behind menus/tool invocation rather than cards on the initial screen.

## Automation safety
- Never promise unrestricted control of every Android app.
- Accessibility may not work on secure screens, custom canvases, protected dialogs or apps that block automation.
- Ask for confirmation before sending messages, deleting files, payments, purchases, account/security changes, posting or exporting/sharing content.
- Never bypass Android security, authentication, biometric prompts or app access controls.
- Do not execute arbitrary shell commands generated by a model. Use an allow-listed action registry and sandbox.
- Add timeout, retry budget, state verification, action history and immediate stop.

## Engineering requirements
- Use modular architecture, typed interfaces, input validation, structured logs with secrets redacted, error boundaries and unit tests.
- Add secure secret storage, TLS, rate limits, request size limits, CORS allowlist, authentication if remotely hosted, and abuse protection.
- Keep 2 GB RAM devices in mind: lazy-load modules, minimize dependencies/animations, limit caches, avoid large local models by default, and test on a real low-memory Android phone.
- Include build instructions, environment template, permissions matrix, threat model, test plan and known limitations.
- Do not mark a feature complete unless its end-to-end implementation is real and tested.
